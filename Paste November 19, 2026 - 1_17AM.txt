PART I — BILLING ENGINE REQUIREMENTS

This section defines the core functional behaviour.

Do not simplify these requirements.

1. Medicine search

Staff must be able to:

- Search medicines by name.
- Use a USB keyboard-wedge barcode scanner.
- Search manually when the barcode is unknown.

Known barcode mappings must be handled internally.

Do not introduce a manual barcode-generation or barcode-registration screen.

If an unknown barcode is scanned:

- Show a clear "Medicine not found" message.
- Permit manual medicine search.
- Never accidentally add a previously selected medicine from stale search results.

The barcode identifies a product, not necessarily its individual batch.

Batch numbers and expiry dates remain separately managed.

2. Search safety

Use Qwen Batch 2R as the corrected baseline.

Verify:

- Changing the search query immediately invalidates outdated results.
- Previous medicine selections cannot be accepted against a new query.
- Stale asynchronous results cannot overwrite current results.
- Fast scanner input cannot select an outdated medicine.
- Search requests do not grow into an unbounded number of parallel operations.
- Search is disabled during finalisation.

3. Medicine cart

The cart must:

- Add selected medicines.
- Allow quantity editing.
- Remove selected rows.
- Show readable quantities and amounts.
- Merge duplicate entries for the same medicine where the backend expects a merged quantity.
- Keep backend calculations authoritative.

Use integer quantity thousandths.

For example:

- 1.000 unit = 1000.
- 2.500 units = 2500.

Do not use floating-point quantities for business calculations.

4. FEFO batch allocation

FEFO means First Expiry, First Out.

The backend must select eligible batches in the earliest-expiry order.

If one medicine requires more stock than its earliest-expiring batch contains, the system must allocate the remaining quantity from the next eligible batch.

The UI must not let staff choose batches manually.

Never sell:

- Expired stock.
- Quarantined stock.
- Blocked stock.
- Inactive medicines.
- Zero-stock batches.
- Otherwise ineligible stock.

Eligibility must be checked again during invoice finalisation.

Do not trust stock availability shown by an earlier search or preview.

5. Invoice preview

"PreviewInvoice" must:

- Be read-only.
- Use the same business calculations as finalisation.
- Return backend-calculated totals.
- Return the applicable tax breakdown.
- Return FEFO allocation information.
- Return validation issues.
- Never deduct stock.
- Never reserve stock.
- Never permanently consume invoice numbering.
- Never create an invoice record.
- Never create audit or payment records.

Every draft change must invalidate the previous preview immediately.

Generate Invoice must remain unavailable until the preview matches the current draft.

6. Invoice finalisation

"FinalizeInvoice" must re-read the current database state.

It must not trust preview prices, batch quantities or stock allocation.

The following operations must occur in one SQLite transaction:

1. Revalidate the draft.
2. Re-read current medicine information.
3. Re-read eligible batches.
4. Recalculate the invoice.
5. Revalidate payments.
6. Allocate invoice numbering.
7. Insert the invoice header.
8. Insert invoice lines.
9. Insert batch-level deductions.
10. Insert stock movements.
11. Insert payment records.
12. Insert audit records.
13. Mark portable stock data dirty and increment its generation.

Only commit the transaction once all required operations succeed.

If any business write fails:

- Roll back the entire transaction.
- Do not leave a partial invoice.
- Do not leave a partial payment.
- Do not deduct stock.
- Do not consume the invoice sequence permanently.
- Return a clear failure result.

A successful invoice result may only be reported after a successful database commit.

If the invoice is committed but the portable stock snapshot fails to refresh afterward, preserve the successful invoice result and return a warning. Never report that a committed invoice failed.

7. Monetary precision

Use integer paise stored as "long".

Examples:

- ₹1.00 = 100 paise.
- ₹125.50 = 12550 paise.
- ₹999.99 = 99999 paise.

Never use "double" or "float" for financial calculations.

Use explicit checked arithmetic and controlled rounding.

Avoid silent numeric truncation.

8. Discounts

Discounts are excluded from the current billing contract.

Do not introduce:

- Manual line discounts.
- Invoice-level discounts.
- Percentage discount fields.
- Coupon systems.
- Promotional pricing.

Keep the existing agreed zero-discount behaviour.

9. Payment methods

The supported payment methods are exactly:

- Cash.
- UPI.
- Debit Card.
- Credit Card.

Split payment is supported by combining multiple tenders.

There is no generic "Other" payment method.

Example:

Invoice total: ₹850.00

- Cash: ₹300.00
- UPI: ₹550.00
- Remaining: ₹0.00

For a fully paid invoice:

"Sum(payment tenders) == Invoice payable total"

Do not mark a bill fully paid when the amounts differ.

Reject:

- Negative payment amounts.
- Invalid payment methods.
- Overflow.
- Missing required payment information.
- Underpayment when the workflow requires a fully paid invoice.
- Overpayment where the existing contract disallows it.

The UI must not implement its own tax or monetary calculations.

10. Customer information

The following are optional for ordinary billing:

- Name.
- Phone number.
- Address.
- GSTIN.

Do not make every customer field mandatory.

Where verified applicable tax rules require recipient information, validate those specific cases.

Do not invent legal requirements or hardcode unsupported assumptions.

11. Invoice numbering and timestamps

Maintain one sequential invoice-numbering system for this single Windows installation.

Use the existing financial-year and invoice-prefix model.

Invoice numbering must be transaction-safe.

Two consecutive committed invoices must never receive the same number.

A failed invoice must not permanently consume its sequence number.

All invoice timestamps must be generated automatically by the system.

PART M — STOCK SNAPSHOT GENERATION SAFETY

This is another confirmed defect.

The existing application uses:

"stock_snapshot_dirty"

as a Boolean flag.

Both InventoryRepository and Gemini BillingRepository mark it dirty inside their stock-changing transactions.

That is better than marking it only after commit, and you must preserve this transactional behaviour.

However, the StockSnapshotWriter has a concurrency race.

The known race

1. Snapshot writer reads database generation N.
2. A new stock transaction commits generation N+1 and marks data dirty.
3. The old snapshot writer completes.
4. The old writer blindly writes dirty = 0.
5. The file contains an older stock state but is incorrectly considered clean.

This must be fixed.

Required implementation

Introduce a monotonically increasing snapshot generation.

Use a setting such as:

"stock_snapshot_generation"

Rules:

1. Every stock-changing transaction increments the generation inside the same transaction as the stock change.
2. That transaction also marks "stock_snapshot_dirty = 1".
3. Snapshot reading captures the database data and current generation from a consistent SQLite read transaction.
4. The snapshot writer writes to a temporary file.
5. It validates the exact generated file.
6. It safely replaces the previous valid file.
7. Before marking the snapshot clean, it checks that the current generation still matches the captured generation.
8. Mark clean only when both generations are identical.
9. If the generation changed, leave dirty = 1.
10. Never report an old snapshot as current.

Use appropriate locking to prevent concurrent snapshot writers within the application.

Avoid creating unnecessary background thread systems or complex job queues.

The snapshot writer must preserve the existing safe replacement and previous-file recovery behaviour.

If the post-commit snapshot refresh fails:

- The invoice remains successfully committed.
- The database remains marked dirty.
- A clear warning is returned.
- The application can regenerate the file later.

Writers to inspect

At minimum:

- InventoryRepository.SaveStockEntry.
- Gemini BillingRepository.PersistInvoiceInTransaction.
- StockSnapshotWriter.

Identify all other existing stock-changing operations in the supplied source.

Every existing stock-changing write must use the same generation mechanism.

Do not increment the generation outside the business transaction and pretend that closes the crash-recovery gap.
